# Cara Mini App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Telegram mini app that lets Cara staff record an expense with dimensions and read the reports the bot cannot draw, consuming the finished backend API.

**Architecture:** A static React SPA in `mini-app/`, served from Telegram's WebView. It authenticates by exchanging `Telegram.WebApp.initData` for a bearer token held in memory, loads all reference data from one `/api/bootstrap` call, and renders three tabs: Add, Reports, History. No server-side logic; the API is the only authority on validation and permissions.

**Tech Stack:** React 19, Vite, TypeScript, Tailwind 3, Recharts, Vitest, React Testing Library. Node 22 on the host (unlike the PHP backend, this does not run in Docker).

**Spec:** `docs/superpowers/specs/2026-07-31-mini-app-design.md`

## Global Constraints

- All client code lives under `mini-app/`. Do not modify anything in `app/`, `routes/`, `database/` or `tests/` — the API is finished and any gap is a separate card, never a client-side workaround.
- New dependencies allowed: `recharts` (runtime), `vitest`, `@testing-library/react`, `@testing-library/user-event`, `jsdom` (dev). Nothing else without human approval.
- Money is never summed across currencies. Every total, group row, chart series and axis belongs to exactly one currency, as the API returns it.
- Amounts arrive from the API as `amount_minor` (integer) plus `currency`; display uses the currency's exponent from the bootstrap `currencies` map (`{"UZS": 0, "USD": 2, ...}`). Never parse the `amount` string for arithmetic.
- The bearer token is held in memory only. Never `localStorage`, never `sessionStorage`, never a cookie.
- User-facing strings are Uzbek, defined in one module. No hardcoded strings in components.
- The API's 4xx body is the authority on errors. The client never re-implements a domain rule to pre-empt one.
- File size: no component file over ~150 lines. Split before that.
- TypeScript strict mode. No `any`. No non-null assertions on API data.
- Conventional Commits, imperative mood, no Co-Authored-By trailer, no mention of AI tooling.

```tsx
// src/ui/Money.tsx
const GROUP_SEPARATOR = ' '

export function formatMoney(
  minorUnits: number,
  currency: string,
  exponents: Record<string, number>,
): string {
  const exponent = exponents[currency] ?? 0
  const isNegative = minorUnits < 0
  const digits = Math.abs(minorUnits).toString().padStart(exponent + 1, '0')
  const whole = exponent === 0 ? digits : digits.slice(0, -exponent)
  const fraction = exponent === 0 ? '' : `.${digits.slice(-exponent)}`
  const grouped = whole.replace(/\B(?=(\d{3})+(?!\d))/g, GROUP_SEPARATOR)

  return `${isNegative ? '-' : ''}${grouped}${fraction}`
}

type MoneyProps = {
  minor: number
  currency: string
  exponents: Record<string, number>
}

export function Money({ minor, currency, exponents }: MoneyProps) {
  return (
    <span className="tabular-nums">
      {formatMoney(minor, currency, exponents)}{' '}
      <span className="text-xs opacity-70">{currency}</span>
    </span>
  )
}
```

### Task 4: The amount grammar

**Files:**
- Create: `mini-app/src/entry/parseAmount.ts`, `mini-app/src/entry/parseAmount.test.ts`

**Interfaces:**
- Consumes: nothing.
- Produces: `parseAmount(input: string): { amount: string } | null` returning a decimal string in MAJOR units suitable for the API's `amount` field, or null when the input is ambiguous.

This is a port of the backend's `App\Services\Telegram\AmountNoteParser` amount half, minus the note splitting: the mini app has a dedicated amount field, so there is no note to separate. Read `app/Services/Telegram/AmountNoteParser.php` before writing it, and mirror its rules exactly. The client parser is a convenience; the server re-validates every amount, so a disagreement costs a 422 rather than a wrong number. Where the two could differ, prefer refusing.

Rules, from the human rulings recorded in the backend:
- A dot or comma is a THOUSANDS separator, never a decimal point. They are interchangeable.
- With exactly one separator, a short final group pads to three digits: `12.50` is 12500.
- With two or more separators, every group after the first must be exactly three digits, otherwise refuse.
- A magnitude suffix multiplies and may carry a fraction: `k`/`к` and the word forms (`ming`, `mingta`, `тыс`, `тысяча`, `тысяч`, `минг`, `мингта`, `тыщ`, `тыща`, `тыщи`) at 1000; (`mln`, `million`, `millon`, `млн`, `миллион`, `миллон`, `мильон`, `лям`) at 1000000; (`mlrd`, `milliard`, `млрд`, `миллиард`) at 1000000000.
- Spaces and apostrophes never group. `100 000` refuses.
- The result must be positive and at most 15 integer digits.

Behaviour the tests must pin:
- The form starts from `bootstrap.defaults`: type, currency, category and dimension values.
- `canSave` is false while the amount does not parse, and false while any `is_required` dimension has no value. `missingRequired` names them so the UI can point at them.
- Save sends `POST /api/transactions` with a UUID `Idempotency-Key` generated once per attempt, and the same key is reused if the same attempt is retried after a network failure. A NEW key is generated for a new entry.
- On success the form resets to the bootstrap defaults and `lastSaved` holds the created transaction so the toast can offer Undo, which calls `deleteTransaction`.
- A 422 maps its `errors` keys onto fields; the client shows them and changes nothing else. The one exception is a 422 naming `category_id` or `dimension_values`, which means a reference row was deactivated since the bootstrap call: the client refetches `/api/bootstrap`, shows `strings.entry.referenceChanged`, and asks the user to pick again rather than leaving them retrying a choice that can no longer succeed.

## After the plan

The mini app is done when every task is committed, `npm test`, `npm run lint` and `npm run build` are clean, and the app has been opened against the running backend at least once with a real Telegram `initData`.

Two things this plan deliberately does NOT cover, both requiring a human:

- **Uzbek strings.** `src/strings.ts` will be written by an agent and needs a native speaker's review before staff see it, exactly like the bot's strings.
- **Hosting.** The build is static, but Telegram requires HTTPS and the backend needs its CORS and Sanctum stateful domains configured for whatever origin serves it. That is deployment work, tracked in `tasks/T2-transactions-followups.md`, not a task here.

One risk worth naming for whoever executes this: the client's amount grammar duplicates the backend's, and the backend's took eight review rounds to get right. Task 4 cross-checks a sample against the real parser, but the two can still drift the next time either changes. The server re-validates every amount, so the failure mode is a 422 rather than a wrong number, and that is the property to preserve if anyone is tempted to "optimise" by trusting the client.
